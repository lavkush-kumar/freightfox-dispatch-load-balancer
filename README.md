# Dispatch Load Balancer

A Spring Boot REST API that stores delivery orders and fleet vehicles, then generates a capacity-constrained dispatch plan using priority-first assignment and Haversine distance.

## Features

- REST endpoints matching the assignment: submit orders, submit vehicles, retrieve dispatch plan.
- Bean Validation for required fields, positive weights/capacities, and geographic coordinate ranges.
- PostgreSQL persistence; submitting an existing ID updates that record (upsert semantics through Spring Data JPA `saveAll`).
- Deterministic dispatch heuristic: HIGH, MEDIUM, LOW; for each order, choose the capacity-eligible vehicle with the smallest distance from its current simulated position. Ties are resolved by vehicle ID.
- Haversine distance in kilometres using mean Earth radius 6,371.0088 km.
- Explicit list of unassigned orders and reasons.
- Centralized JSON error responses, Swagger UI, Docker Compose, Postman collection, and unit tests.

## Requirements

- Java 21
- Maven 3.9+ (or use the Maven wrapper generated by your IDE)
- Docker Desktop / Docker Engine (recommended for PostgreSQL)
- IntelliJ IDEA (recommended IDE)

## Run with Docker (recommended)

From the project root:

```bash
docker compose up --build
```

The API starts at `http://localhost:8080`; PostgreSQL is exposed on port `5432`.

## Run locally from IntelliJ

1. Install and configure JDK 21.
2. Start PostgreSQL and create a database/user, or start only the database service from `compose.yaml`.
3. Open this folder in IntelliJ IDEA as a Maven project.
4. Configure environment variables if your database credentials differ:
   - `DB_URL=jdbc:postgresql://localhost:5432/dispatchdb`
   - `DB_USERNAME=dispatch`
   - `DB_PASSWORD=dispatch`
5. Run `DispatchLoadBalancerApplication`.

Alternatively run:

```bash
mvn clean test
mvn spring-boot:run
```

## API documentation

- Swagger UI: `http://localhost:8080/swagger-ui.html`
- OpenAPI JSON: `http://localhost:8080/v3/api-docs`

### 1. Submit delivery orders

`POST /api/dispatch/orders`

```json
{
  "orders": [
    {
      "orderId": "ORD001",
      "latitude": 28.6139,
      "longitude": 77.2090,
      "address": "Connaught Place, Delhi, India",
      "packageWeight": 15,
      "priority": "HIGH"
    }
  ]
}
```

Success response (HTTP 202):

```json
{"message":"Delivery orders accepted.","status":"success"}
```

### 2. Submit fleet vehicles

`POST /api/dispatch/vehicles`

```json
{
  "vehicles": [
    {
      "vehicleId": "VEH001",
      "capacity": 100,
      "currentLatitude": 28.7041,
      "currentLongitude": 77.1025,
      "currentAddress": "Karol Bagh, Delhi, India"
    }
  ]
}
```

Success response (HTTP 202):

```json
{"message":"Vehicle details accepted.","status":"success"}
```

### 3. Retrieve dispatch plan

`GET /api/dispatch/plan`

Returns each vehicle's assigned orders, total load, and cumulative one-way travel distance, plus unassigned orders. Import `postman/Dispatch-Load-Balancer.postman_collection.json` into Postman for ready-to-run requests.

## Algorithm and assumptions

1. Orders are sorted by priority (HIGH first, then MEDIUM, then LOW); order ID provides deterministic ordering within a priority.
2. For each order, vehicles without sufficient remaining capacity are excluded.
3. The eligible vehicle with the shortest Haversine distance from its current simulated position is selected.
4. The vehicle's simulated position moves to the assigned order's coordinates; its remaining capacity is reduced.
5. If no vehicle can take an order, it is returned in `unassignedOrders` with a reason.

This is a practical greedy heuristic, not an exact global vehicle-routing solver. The implementation minimizes each next assignment's incremental straight-line distance while respecting the priority and capacity rules. It does not model road networks, traffic, time windows, multiple trips, vehicle speed, or return-to-depot legs. Those are possible production extensions. The dispatch plan is recomputed from stored starting vehicle locations each time it is requested; generating a plan does not mutate fleet master data.

## Error handling

- `400 Bad Request`: invalid fields, invalid coordinates, empty input arrays, or duplicate IDs within one submitted batch.
- `409 Conflict`: persistence-level data conflict.
- `500 Internal Server Error`: unexpected server failure (internal exception details are not exposed).

## Tests

Run `mvn test`. Tests cover Haversine distance, invalid coordinates, priority ordering, capacity enforcement, nearest eligible vehicle selection, and no-fleet handling. For a hiring submission, add further integration tests against the controller and PostgreSQL, plus load/performance tests for the expected production volume.

## Production hardening notes

Before deploying to a real fleet, add authentication/authorization, request-size limits, database migrations (Flyway), structured logs/metrics/tracing, idempotency policy, concurrency control for simultaneous dispatch runs, and a routing provider for road distance. Set secrets through a secret manager rather than the sample Compose credentials. `ddl-auto: update` is convenient for this take-home; replace it with validated migrations for production.
